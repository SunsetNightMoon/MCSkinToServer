# 邮箱与账号找回

每个账号有一个主邮箱，外加一个可选的备用邮箱。本文讲三条容易误解的口径。

## 1. 一个邮箱只绑一个号

数据库建了两个唯一索引：

- `users_email_lower_uidx` on `lower(email)` —— 主邮箱全局唯一，大小写无关。
- `users_backup_email_lower_uidx` on `lower(backup_email)`（带 `IS NOT NULL` 条件）—— 备用邮箱之间唯一。

但**跨列**（A 的主邮箱同时是 B 的备用邮箱）索引管不到，只能靠应用层查重：注册、绑备用邮箱、改邮箱三条路径都会查对方账号的两个槽位。

万一历史数据已经造出冲突，登录**不会任选一个账号**，而是两边都按凭据错误收口 —— 否则那个地址就成了「猜中即登进某个号」的入口。冲突只在服务端记一条日志（数据不变量被破坏需要人工核查），对客户端不给任何区别，免得登录端点变成冲突探测器。

## 2. 已验证的备用邮箱是登录凭据

| 场景 | 主邮箱 | 已验证备用邮箱 | 未验证备用邮箱 |
|---|---|---|---|
| 网页登录 | 可以 | 可以 | 不行 |
| 启动器 `authenticate` / `signout` | 可以 | 可以 | 不行 |
| 「要求邮箱验证」门槛 | 需主邮箱已验证 | 视为已满足 | — |
| 找回密码发起 | 可以 | 可以 | 不行 |
| 注册时占用该地址 | 唯一索引 + 应用层 | 应用层查重 | 应用层查重 |

- 大小写不敏感，与主邮箱同一口径。
- 用备用邮箱登录时视为满足 `REQUIRE_EMAIL_VERIFICATION`：备用邮箱存在的意义就是主邮箱收不到信时的兜底，再卡一道主邮箱门槛等于把兜底堵死。
- **未验证的备用邮箱不参与认证**。「已绑但未验证」是刷号方最爱下手的状态，给它认证能力等于开无限量入口。正常流程下 `users.backup_email` 只在点完验证链接那一刻才写入（pending 状态只活在令牌表里），认证查询仍显式带验证条件作为防线。

## 3. 找回密码是交叉投递的

主邮箱或已验证的备用邮箱都能发起重置；账号有**另一个**已验证邮箱时，重置信发到那个邮箱。

这样单个信箱失守（被拖库、被盗、长期不看）不再足以改密码。

- 另一槽位不存在或未验证时，回落到同槽投递 —— 否则这类账号只能找超管人工处理，那是更糟的结果。
- 交叉投递的重置**不会**顺带把主邮箱标成已验证：那封邮件证明的是备用信箱的归属。宁可少标一个状态，绝不假造。
- 找回密码页面**不回显投递地址**。回显等于替探测者确认「这个账号存在」，也会让收件人去翻错的那个邮箱。

## 4. 已知缺口（记录，未实现）

登录限流按**提交的地址**分桶，因此同一账号有主/备两个独立桶，等于把「对同一账号猜密码」的配额翻倍。收紧方向是把桶归一到解析出的账号 ID，需要在认证路径内计数。
