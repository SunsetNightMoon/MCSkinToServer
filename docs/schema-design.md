## 1. 设计原则

### 1.1 单一 schema 来源

plan3 的 P0 病灶是四套 schema 来源并存（迁移文件、SetupService 内联 DDL、测试 DDL、一次性脚本）。
本草案确立的规则：

- **只有 `schema/` 目录下的迁移文件是合法 schema 来源**。
- 迁移文件命名 `NNNN_name.sql`（NNNN 四位数字从 0001 递增）；runner 拒绝命名不合法或版本号重复的 `.sql` 文件。
- **迁移文件内禁止 BEGIN/COMMIT 等事务控制语句**，事务边界由迁移 runner 拥有（每个迁移在单个事务内执行）。
- runner 维护版本表 `schema_migrations(version, checksum, applied_at)`：已应用且 checksum 一致则跳过（幂等）；checksum 漂移则拒绝执行（schema 漂移检测）；执行失败即回滚且不记录版本，CLI 以非零码退出阻止服务启动。
- 安装向导（Setup）不允许建表，只允许写入 `system_settings` 和初始数据。
- 测试使用与生产相同的迁移文件构建临时库，不再维护独立测试 DDL。
- PostgreSQL 与 SQLite 的差异只允许体现在**类型映射和 DDL 变体**上，表名、列名、约束、索引必须一一对应；等价性由任务 2 的双库迁移 smoke test 强制保证。

### 1.2 PostgreSQL 为 canonical，SQLite 为映射变体

以 PG 版本为评审基准；SQLite 版本由固定的类型映射规则机械生成（见 §2）。

### 1.3 ID 策略：全 UUID + 展示用 user_uid

- 所有实体主键为 UUID（应用层生成，小写带连字符，存 PG `UUID` / SQLite `TEXT`）。
- 理由：plan3 的 `users.id` 与 `profiles.id` 已是字符串 UUID，沿用可**在数据迁移时原样保留 ID**，避免全量重映射。
- `users.user_uid` 保留为对外展示的递增数字号（产品惯例），但它是**展示字段，不是关联键**——所有外键一律走 UUID。
- UUID 的 Yggdrasil 边界规则：内部统一带连字符小写；协议适配层输出无连字符格式（analysis §6.3 的边界统一要求）。

### 1.4 时间策略：应用层写入，禁止数据库时间函数

- 所有时间列为应用层写入的 UTC 值；**业务 SQL 中禁止出现 `datetime('now')`、`now()` 等任何数据库时间函数**（根除 plan3 §7.4 的跨库 bug 类）。
- 因此 DDL 中也没有 `DEFAULT CURRENT_TIMESTAMP`——时间一律由应用服务显式提供，测试因此完全确定。
- 表达式格式：PG `TIMESTAMPTZ`；SQLite `TEXT`（ISO-8601 UTC，如 `2026-09-20T06:00:00.000Z`）。

### 1.5 权限字段：两个正交枚举 + 审核状态

替代 plan3 的 `permission_level` / `is_public` / `is_downloadable` 三重冗余：

```text
visibility:      private | public        （谁能在公开库看到）
download_policy: owner_only | public     （谁能下载原图）
review_status:   pending | approved | rejected
```

- 公开库可见 = `visibility = 'public' AND review_status = 'approved'`
- 可下载 = owner OR (`visibility = 'public'` AND `download_policy = 'public'`)
- plan3 的 `public_no_download` 在 **API 适配层**映射为 `visibility='public' + download_policy='owner_only'`（blueprint §3.4），数据库不再存储旧名。

### 1.6 令牌只存 hash

- `tokens.token_hash` = sha256(明文 token)，明文只在签发响应中出现一次。
- 数据库不保存明文 access token（plan3 的 P0 冲突列 `token` / `access_token` 双列就此消灭）。
- 查找方式：按 `token_hash` 精确查询（唯一索引）。

### 1.7 Blob / Asset / ProfileAssignment 分离

plan3 全局 hash 去重会把"文件所有权"和"素材使用权"混在一起（analysis §8.3）。本草案：

- `blobs`：不可变文件对象，按 `sha256` 全局唯一 → 相同文件只存一份。
- `assets`：用户拥有的素材记录（皮肤/披风统一，`kind` 区分），引用 `blob_id`。
- `profile_assets`：角色当前绑定，`(profile_id, slot)` 唯一 → 每角色一个皮肤槽 + 一个披风槽。
- 删除用户时：assets 级联删除 → blob 按引用计数由清理任务异步回收（`blob_id` 外键 RESTRICT 防止误删仍被引用的文件）。

## 2. PostgreSQL / SQLite 类型映射

| canonical（PG） | SQLite | 说明 |
|---|---|---|
| `UUID` | `TEXT` | 小写带连字符；边界层负责无连字符转换 |
| `TIMESTAMPTZ` | `TEXT` | ISO-8601 UTC；应用层写入 |
| `BOOLEAN` | `INTEGER` + `CHECK (x IN (0,1))` | 适配层统一映射为 boolean |
| `JSONB` | `TEXT` | SQLite 侧用 JSON1 函数 |
| `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `INTEGER`（应用层分配） | 仅 `user_uid`；SQLite 在插入事务内 `MAX+1`（单写者场景） |
| `TEXT + CHECK` 枚举 | `TEXT + CHECK` | 不使用 PG 原生 ENUM，便于迁移 |
| `lower(email)` 表达式唯一索引 | 同 | 两库均支持表达式索引 |

其他固定规则：

- SQLite 连接必须 `PRAGMA foreign_keys = ON`（由数据库适配层负责，迁移 runner 也要开）。
- 迁移文件成对存放：`schema/postgresql/NNNN_*.sql` 与 `schema/sqlite/NNNN_*.sql`，编号一一对应。

## 3. 表清单（15 张）

### 3.1 身份与权限

#### `users` — 站点账号（与 Minecraft Profile 分离）

关键决策：

| 决策 | 内容 | 理由 |
|---|---|---|
| 权限模型 | 只保留 `role TEXT`（user/admin/super_admin）；`level` 从 schema 中删除 | plan3 的 `role`+`level` 双字段可能不一致（analysis §6.2）；`level` 仅作为旧 API 兼容映射存在 |
| 封禁表达 | `ban_permanent BOOLEAN` + `banned_until TIMESTAMPTZ` 两列 + CHECK 互斥 | plan3 用字符串 `'permanent'` 塞进时间列，无法类型化；两列表达两个正交事实 |
| email 唯一 | `lower(email)` 表达式唯一索引 | 应用层写入前规范化为小写；防止大小写变体绕过唯一性 |

#### `profiles` — Minecraft 角色

- `name` UNIQUE（3-16 位 `[A-Za-z0-9_]`，应用层校验格式）。
- `name_changed_at`：30 天改名冷却的计时基准。
- **不再持有 `skin_id` / `cape_id`**——当前绑定改由 `profile_assets` 表达。

### 3.2 文件对象与素材

#### `blobs` — 不可变文件对象

```text
id, sha256(UNIQUE), storage_key(UNIQUE), content_type, byte_size, width, height, created_at
```

- `sha256` 小写 hex；`storage_key` 为存储 provider 相对 key（内容寻址，如 `blobs/ab/ab12….png`）。
- 数据库**只存 object key，绝不存完整 URL**（blueprint §4）；对外 URL 一律由存储端口 `publicUrl(key)` 生成。

#### `assets` — 素材（皮肤/披风统一）

- `kind IN ('skin','cape')`；`model_type` 仅皮肤可填（CHECK 约束：skin ∈ default/slim，cape 必须为 NULL）。
- 权限三字段见 §1.5；`ai_generated`、`admin_warning` 保留产品能力。
- `license TEXT NOT NULL DEFAULT 'CC0'`（可选值由应用层定义，不加 CHECK 以免限制产品迭代）。
- `view_count` / `download_count` 为行内计数器（P3 需求）。
- 索引：owner 查询、blob 引用计数、公开库查询 `(kind, visibility, review_status, created_at)`。

#### `profile_assets` — 角色当前绑定

- `(profile_id, slot)` 唯一 → 结构上保证每角色每槽位一条。
- `slot` 与 `assets.kind` 的一致性由应用服务保证（CHECK 无法跨表表达，写入测试覆盖）。

#### `favorites` — 收藏（皮肤披风统一）

- 复合主键 `(user_id, asset_id)`；plan3 的 `skin_favorites` / `cape_favorites` 两表自然合一。
- "发布者默认收藏一条、用户不能收藏自己的素材"是**领域服务规则**（route-inventory §5），不在 schema 层表达，由服务与测试保证。

#### `asset_reviews` — 审核流水

- `assets.review_status` 是当前态，本表是历史流水（谁在何时批准/拒绝、理由）。
- `reviewer_user_id` 可空 + `ON DELETE SET NULL`：审核人账号被删除时流水保留但匿名化，不阻塞账号删除。

### 3.3 令牌与会话

#### `tokens` — 统一令牌表（blueprint §3.5 原样落地）

```text
id, token_hash(UNIQUE), token_type(web|yggdrasil), client_token,
user_id, profile_id(可空), issued_at, expires_at, last_used_at, revoked_at
```

- `profile_id`：Yggdrasil selectedProfile 绑定；Profile 被删除时 `SET NULL`（令牌存活，绑定解除，客户端需 refresh 重选）。
- `client_token` 存明文：它是客户端提供的回显标识，不是凭据。
- `CHECK (expires_at > issued_at)`。

#### `minecraft_sessions` — join/hasJoined 短会话

- 字段：`token_id`, `profile_id`, `server_id`, `created_at`, `expires_at`。
- TTL 约 30–60 秒；`expires_at` 为应用层 UTC 参数（消灭 `datetime('now','+30 seconds')`）。
- 查询索引 `(server_id, profile_id)`（hasJoined：按 server_id + 角色名联查 profiles.name UNIQUE）+ 过期清理索引。
- plan3 `sessions` 表的数据是短命数据，迁移时**直接丢弃，不导入**。

#### `login_sessions` — Web 登录会话登记

- `user_id`, `token_id`, `ip`, `user_agent`, `created_at`, `last_seen_at`。
- 用途：审计 + 前端"登录设备管理 / 登出所有设备"（后者通过批量 `revoked_at` 实现）。

### 3.4 账号辅助流程

- `email_verification_tokens` / `password_reset_tokens`：同构小表（`token_hash` UNIQUE、`expires_at`、`used_at`）。按 blueprint 表清单保持分表；若后续想合并为 `one_time_tokens(purpose)` 是一次普通迁移。
- `oauth_accounts`：`(provider, provider_account_id)` 唯一。provider CHECK 白名单（github/microsoft），新增 provider 走迁移——这是刻意的显式变更。

### 3.5 黑名单与系统设置

- `blacklist_entries`：`kind IN ('email','ip')` + `value` 唯一；`expires_at` NULL = 永久。
- `system_settings`：`key TEXT PK` + `value JSONB/TEXT`，替代 plan3 的 `system_config` 纯字符串 kv。安装完成状态也存这里（`setup.complete` 等），Setup 不再写 `.env`。

### 3.6 关系总览

```text
users ─┬─ 1:N ─ profiles ── 1:1/slot ─ profile_assets ─ N:1 ─ assets ─ N:1 ─ blobs
       │                                      └── N:M favorites（指向 users+assets）
       ├─ 1:N ─ tokens ─┬─ 1:N ─ minecraft_sessions ─ N:1 ─ profiles（可空绑定）
       │                └─ 1:N ─ login_sessions
       ├─ 1:N ─ oauth_accounts / email_verification_tokens / password_reset_tokens
       └─ 1:N ─ asset_reviews（审核人，可空）/ blacklist_entries（操作人，可空）
```

## 4. 与 plan3 的关键差异

| plan3 | 本草案 | 理由 |
|---|---|---|
| `tokens` 有 `token`/`access_token` 明文双列，PG 初始 schema 缺 `token` 列 | 单一 `tokens` 表，只存 `token_hash` | 消灭 P0 字段契约冲突；明文不入库 |
| `sessions` 用 `datetime('now','+30 seconds')` | `minecraft_sessions`，应用层 UTC 参数 | 消灭 P0 跨库时间函数 |
| `skins` + `capes` 两张同构表 | 单一 `assets` + `kind` | 权限/审核/收藏语义一次定义 |
| `file_path` 直存 + URL 拼接 | `blobs`(sha256 唯一) + `assets.blob_id` | 文件对象与素材元数据分离 |
| profiles 直挂 `skin_id`/`cape_id` | `profile_assets` 绑定表 | 统一绑定关系，天然可扩展 |
| `permission_level`/`is_public`/`is_downloadable` 三字段 | `visibility` + `download_policy`（+ `review_status`） | 单一事实来源 |
| `role` + `level` 双权限字段 | 仅 `role` | `level` 降级为 API 兼容映射 |
| `banned_until` 塞字符串 `'permanent'` | `ban_permanent` + `banned_until` | 类型化，CHECK 互斥 |
| `skin_favorites` / `cape_favorites` | 单一 `favorites` | assets 合并后自然统一 |
| 无审核历史 | `asset_reviews` 流水 | 审计 |
| `system_config` 字符串 kv | `system_settings` JSON | 结构化配置 |
| 四套 schema 来源 | 仅 `schema/` 迁移文件 | 单一事实来源 |

## 5. 放弃的内容

- `skin_tags`：PG 初始 schema 中存在但业务没有闭环（route-inventory §8），不迁移。未来需要标签时走正常迁移加表。
- `JWT_SECRET` 与 jsonwebtoken 依赖：plan3 无实际 JWT 流程，新 schema 的 tokens 表即完整凭据模型。
- 运行时写 `.env`：schema 层面没有对应物；配置在启动时读取（blueprint §5.1）。

## 6. plan3 → MCSTS 数据迁移映射预览（供任务 6 盘点脚本参考）

| plan3 | MCSTS | 变换 |
|---|---|---|
| `users.id`（字符串 UUID） | `users.id` | 原样保留 |
| `users.user_uid` | `users.user_uid` | 原样保留；导入后 PG 需 `setval` 校准 identity 序列 |
| `users.email` | 同 | 小写规范化（先查重再写入） |
| `users.level` + `role` | `role` | 0/1/2 → user/admin/super_admin（不一致时以 role 为准并记录差异） |
| `users.banned_until = 'permanent'` | `ban_permanent = TRUE` | 日期字符串 → `banned_until` |
| `profiles` | 同 | id/name/user_id/name_changed_at 原样；`skin_id`/`cape_id` 改写入 `profile_assets` |
| `skins`/`capes` 行 | `assets` 行 | `permission_level` → visibility+download_policy 映射；`is_ai_generated` → `ai_generated` |
| 文件（按 `file_hash` 去重） | `blobs` | 每个不同 hash 建一个 blob；`storage_key` 重写为内容寻址 key；物理文件搬运由离线工具做 |
| `tokens` | `tokens` | **明文 token 现场哈希**后写入 `token_hash`（旧令牌保持有效）；web/yggdrasil 按 usage 归类 |
| `sessions` | — | 短命数据，丢弃 |
| `skin_favorites` / `cape_favorites` | `favorites` | 两表合并（asset_id 重映射） |
| `blacklist` | `blacklist_entries` | 按 kind 拆分 email/ip |
| `oauth_accounts` | 同 | 原样 |
| `system_config` | `system_settings` | 字符串 → JSON 值（逐 key 定义） |
| 孤儿文件（盘点发现） | — | 不导入，列入报告 |

迁移工具定位：离线、可重复、可中断恢复（blueprint §9），不复用 Web 安装向导。

## 7. 待决策问题（评审时定）

1. **assets 删除语义**：当前为硬删除 + 级联（审核流水随之消失）。是否需要 `deleted_at` 软删除保留审核现场？（软删除会污染所有查询，需要全局过滤纪律）
2. **user_uid 在 SQLite 的分配**：`MAX+1`（单写者够用）是否接受？或引入 `id_sequences` 表？
3. **download_policy 枚举值**：`owner_only | public` 命名是否 OK（API 层映射 plan3 的 `public_no_download`）？
4. **oauth provider 白名单 CHECK**：加 provider 需要一次迁移，是否接受？
5. **email/password 令牌表分立 vs 合并** `one_time_tokens(purpose)`：当前按 blueprint 分立。
6. **minecraft_sessions 是否记 `consumed_at`**（hasJoined 一次性消费）还是纯 TTL：当前纯 TTL，与 plan3 行为一致。
